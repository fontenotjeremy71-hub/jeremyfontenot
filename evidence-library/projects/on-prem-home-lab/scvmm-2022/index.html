Implementation and troubleshooting

Build, remediate, onboard, and verify.

01

Server and database foundation

Prepared VMM01 on Windows Server 2022 and installed SQL Server 2022 Developer as the local database platform for the VMM management server.

02

ADK and WinPE prerequisites

Installed Windows ADK Deployment Tools and the Windows PE add-on. When VMM could not locate the Component Studio libraries, verified that the DLLs existed under WSIM\amd64 and copied the WSIM architecture files into the root path expected by Setup.

03

Dedicated service identity

Created JFAD\svc_scvmm, configured the account for the lab service role, added it to VMM01's local Administrators group, and used it for the Virtual Machine Manager service.

04

SCVMM installation

Installed both the SCVMM 2022 management server and VMM console, configured the local VMM database and library, retained standard service ports, and verified a successful console connection to VMM01.

05

Hyper-V host onboarding

Added HVHOST01 as a trusted-domain Hyper-V host. The first agent deployment exposed an unreachable ADMIN$ path; TCP 445 testing isolated the firewall block, File and Printer Sharing was enabled, and the retry completed with host status OK.

06

VM discovery and control

SCVMM discovered APP01 on HVHOST01. Remote power-on completed successfully, guest information populated, and VM Viewer confirmed an interactive APP01 console session.

07

Laptop console over OpenVPN

Installed only the VMM console MSI on the non-domain-joined laptop, connected to VMM01 with domain credentials through OpenVPN, and validated TCP 8100 access plus APP01 control and console viewing.

08

Temporary access cleanup

Removed the temporary SCVMM installer SMB share, deleted the laptop's cached SMB connection, and removed the temporary OpenVPN TCP 445 rule. TCP 8100 remains as the scoped VMM console path.

August 15, 2026 operational update

Extended the lab from host management into VMM logical networking and repeatable operations.

This working session focused on correcting host-management health, bringing the existing Hyper-V network under VMM control, and exercising APP01 through the VMM abstraction layer while preserving the isolated 10.10.20.0/24 lab behind pfSense.

09

Recovered VMM host-agent health

HVHOST01 initially reported Needs Attention with VMM error 12704 even though vmms and SCVMMAgent were running and both server and agent were version 10.22.1287.0. WinRM tests passed. A VMM Run As account named HVHOST01 Management was created with the validated domain-management credential and assigned under Host Access. After refresh, host status, network, WinRM, agent service, and agent version all reported OK.

10

Modeled the isolated AD network

Validated the VMM logical network ad and network site AD-10.10.20.0-24 for subnet 10.10.20.0/24. The static VMM IP pool spans 10.10.20.201 through 10.10.20.220 and VMM reports the logical network as Fully compliant.

11

Resolved logical-switch conversion blockers

The existing External-LAN standard switch could not convert while the VMM logical switch used a different minimum-bandwidth mode and uplink teaming mode. The Host management port profile weight was cleared, HomeLab-Logical-Switch was changed to Absolute bandwidth mode, and its uplink mode was changed to No Uplink Team to match the single-adapter standard switch.

12

Converted to a VMM logical switch

Converted External-LAN into HomeLab-Logical-Switch using the HomeLab-Uplink uplink profile. VMM completed the host-change job successfully, Hyper-V reported the new external switch name, and the host management vNIC retained 10.10.20.102/24, gateway 10.10.20.1, and DNS 10.10.20.10.

13

Applied a VM traffic classification

Adjusted the built-in Medium Bandwidth Adapter profile so it was compatible with the logical switch's Absolute bandwidth mode, mapped the Medium bandwidth classification into HomeLab-Logical-Switch, and assigned that classification to APP01's virtual network adapter.

14

Validated guest network and domain services

APP01 remained connected to HomeLab-Logical-Switch with status Ok. Inside the guest, 10.10.20.103/24, gateway 10.10.20.1, and DNS 10.10.20.10 remained intact. Gateway ping succeeded, DC01 resolved to 10.10.20.10, and TCP 389 to the domain controller succeeded.

15

Exercised checkpoint lifecycle

Created the VMM checkpoint Pre-VMM-Lab-Changes while APP01 remained running, verified the checkpoint in APP01 properties, then deleted it and confirmed the checkpoint list returned to empty.

16

Protected resource headroom

Measured HVHOST01 at four logical processors and about 8 GB RAM. APP01 Dynamic Memory was already configured with 2048 MB minimum, 4096 MB startup, and 6144 MB maximum; its active assignment had settled to 2 GB with memory status OK. No additional Windows VM was deployed so the nested host retained practical headroom.

Scope and limitations

A working management lab, not an enterprise VMM deployment.

The evidence supports a single SCVMM 2022 management server, one managed nested Hyper-V host, one observed guest, a VMM logical network and IP pool, conversion of an existing external switch into a VMM logical switch, VM port classification, remote lifecycle control, checkpoint handling, VM Viewer access, and a scoped OpenVPN management path. It does not prove clustering, high availability, live migration, Storage Spaces Direct, enterprise scale, production availability, security assurance, or management of Proxmox guests through VMM.
